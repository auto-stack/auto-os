# 桌面组织演进：DeskBox 参考分析（战略候选）

状态：参考分析，不占用全局 Plan 编号，不宣称实现，不冻结接口；
日期：2026-10-15（同日两次用户裁定：桌面心智与盒子模型见 §5；
功能细化暂缓——待用户启动桌面整理窗口时再按本文立项详析，见 §7）。
触发：用户观察到 AutoOS 桌面仍似传统 Windows
桌面（快捷方式散布 + 一个小组件面板），提议评估开源项目 DeskBox
（<https://github.com/Tianyu199509/DeskBox>）的组织形式可否参考。

## 1. 现状证据（AutoOS 桌面已有能力）

| 维度 | 现状 | 证据 |
|---|---|---|
| 桌面图标面 | 固定 8 列网格（格宽 80px / 格高 72px / 图标 48px，PLAN-012 W5），图标本体 = pinned ∪ 自定义虚拟条目，未定位图标列主序填充 | `shell/desktop.at`（DesktopSurface，`__desktop_icons` 注入 {id,icon,label,src,color}，src 仅 pinned\|custom） |
| 拖放与位置记忆 | press-press 两段式拖放换格；storage 键 `shell.desktop.positions` + 每壁纸键控 `wp/<fp>`（SD-04） | 同上 + `docs/specs/shell/showdesk-icons.md`、`showdesk-wallpaper.md` |
| 分组/盒子/堆叠 | **无**。全库无 fence/盒子/图标分组实现；「虚拟文件夹」仅是 Design 25 S9 表面盘点中的未落项 | auto-lang `docs/design/autoui/desktop-shell.md` S9 行 |
| 小组件 | DashboardPanel 统一面板（8×2 网格直显各 App `view mini` 活渲染面，face pin/span/tab），非自由摆放的独立部件 | `shell/dashboard.at`；宿主 `has_named_view("mini")` 发现（renderer.rs） |
| 承载对象 | **只有 app 快捷方式，没有文件**。桌面图标是注册表/自定义条目，不映射文件系统 | `__desktop_icons` 协议（desktop.at 头注） |
| 架构底座 | WM-as-app：桌面层是特权 .at App 的图标面，拖放/菜单/持久化全走投影协议与 storage，宿主单 OS 窗口合成 | Design 23 R1/R2/R8（auto-lang `docs/design/autoui/virtual-desktop.md`） |

即：组织形式的缺位是产品层面的（没做），不是架构层面的（做不了）。

## 2. DeskBox 是什么（证据摘要）

| 维度 | 事实 |
|---|---|
| 定位 | 免费开源 Windows 桌面整理器，「现代开源版 Stardock Fences」；核心承诺 = 真实文件夹背书的文件部件（real-folder-backed file widgets），Todo/速记/搜索/天气/音乐为附加 |
| 活跃度 | 6,936 stars / 365 forks；2026-06-11 创建，2026-10-14 仍在推送；4,487 项测试；docs/architecture/ 下 30+ 专项契约文档 |
| 技术 | C#/WinUI 3/.NET 10 Native AOT/Windows App SDK 2.5.1 + Rust 原生 Shell 层（约 350K 行：原生右键菜单托管、缩略图代理、快捷方式/回收站/音量/搜索 ABI） |
| 集成形态 | **不替换 Explorer**——在原生桌面上叠一层自由摆放的 WinUI 3 部件窗口（Mica/Acrylic 材质、桌面层附着） |
| 许可 | **GPL-3.0-only**：只能参考思想，零代码/零资源引用（本也不同栈，无实际成本） |

## 3. 设计分析：把它的设计拆成两层

### 3.1 产品/交互模型层（值得吸收）

1. **盒子 = 真实文件夹的活窗口**。盒子不是虚拟容器：新建盒子即建受管文件夹，或「映射既有文件夹不搬家」；拖入拖出即真实 copy/move（遵循 Windows 语义、跨卷决策、修饰键建快捷方式、原生拖放反馈）。心智模型从「桌面 = 图标集合」换成「桌面 = 若干文件夹的活视图」。
2. **盒子内治理**：icon/list 双布局、手动/规则排序、**堆叠**（文件手动或自动成 stack，盒内展开或 3×3/5×5 popover 展开且共享网格密度）、紧凑密度与每部件图标尺寸。
3. **桌面一键整理**：按类别「先预览再移动」——每类可选新建文件夹或并入既有盒子；下载/解压/同路径替换落定后自动归类（dwell 从实时到 12h 可配）。整理是显式、可预览、可解释（失败分类报告）的，不是静默搬家。
4. **部件分组与胶囊**：多部件 merge 成组（标题栏/滚轮/Ctrl+Tab 轮换成员，不改各自背书数据）；部件可折叠成 smart capsule（hover 展开、敏感内容折叠态隐藏）、胶囊可拼成可移动条。
5. **多显示器布局治理**：部件按显示器硬件身份（PnP device-interface id）绑定，每个显示器组合保存独立布局；拔显示器宽限期后比例迁移或折叠成胶囊，插回原位精确复原。
6. **性能治理哲学**：隐藏/非活动部件按策略释放可重建 UI、解码位图、图标缩略图（Balanced/Saver/Custom 三档）；启动等 Explorer 图标宿主稳定后才附着，不干扰系统自身的图标位置恢复。

### 3.2 Windows 集成工程层（不必参考——架构差异天然免疫）

DeskBox 工程复杂度的大头在「外来者套在 Explorer 桌面上」这件事本身：
桌面层附着与 z 序恢复、原生拖放 ABI、重命名 IME、UAC 完整性级别差异、
Explorer 崩溃/睡眠/DPI 变化的恢复序列、Win10/Win11 双栈差异、每项都有
专项契约文档和冒烟矩阵。AutoOS 是自有窗口系统：桌面图标本来就是
DesktopSurface 的内容，拖放/菜单/持久化全在投影协议与 storage 内，
上述问题类**整体不存在**。参考价值仅在其「高风险面清单 + 手工回归
检查单」的工程方法（每接缝一份契约文档 + AOT 冒烟矩阵），与我们的
spec/契约纪律同构，可视为方法印证而非新知。

## 4. 裁定：参考什么、不参考什么

| 项 | 裁定 | 理由 |
|---|---|---|
| 盒子/堆叠/一键整理的**组织形式** | **吸收** | 经 7k 星用户验证的桌面组织交互；直接补齐 S9「虚拟文件夹」未落项 |
| folder-backed 语义（盒子=真实文件夹） | **已裁定转译**（2026-10-15 用户裁定，见 §5：入口盒子 + 资料盒子混合路线） | 桌面不放散置文件；资料盒子背书非桌面目录 |
| 独立自由浮窗部件形态 | **不照抄** | 与 AutoOS 桌面层 z 槽/网格 DSL 冲突；盒子更自然落点是 DesktopSurface 的一种图标面容器组件（挂 463 桌面层 z 槽），不是浮窗 |
| 胶囊（折叠态） | 吸收为盒子/部件折叠态设计 | 小成本高收益的交互词汇 |
| 多显示器布局键控 | 登记备查，暂不设计 | AutoOS 当前单 OS 窗口合成（R2），多显示器是独立量级话题 |
| 性能治理（隐藏即释放/惰性重建） | 原则登记 | 与 iced/VM residency 思路相通，非桌面专属 |
| Windows 集成 hack | 不参考 | 架构差异（§3.2） |
| 代码 | 零引用 | GPL-3.0-only，且不同栈 |

**结论：值得参考**——学它的产品模型（组织形式、整理交互、折叠词汇）
与 UI 词汇（§6），不学它的工程形态（叠窗、原生 ABI）；承载对象的
转译已于 2026-10-15 用户裁定（§5：桌面 = app 入口组织面 + 受限的
资料盒子）。

## 5. 用户裁定（2026-10-15）：桌面心智与盒子模型

DeskBox 解决的原始问题是「文件与快捷方式混居」，所以盒子必须背书
真实文件夹。AutoOS 桌面没有这个问题——图标全是 app 入口。用户裁定
（原文转述）：**桌面不放文件**；桌面主要用来整理各种 app 入口，做成
类似手机/平板的形式；快捷方式没问题；**资料类型的盒子**可以指定背后
对应的实际目录（非桌面目录），盒内直接看到文件；资料盒子 UI 考虑与
file-manager 共享；除组织方式/堆叠/整理/胶囊外，**UI 也参考 DeskBox**
（当前桌面 UI 较粗糙，见 §6）。

裁定后的桌面模型（原 §5 路线 A/B 之择落定为**混合路线**）：

| 元素 | 语义 | 域/依赖 |
|---|---|---|
| 桌面本体 | app 入口组织面（手机/平板 launcher 心智）：散置单图标 + 盒子，**不承载散置文件** | shell 域 |
| 入口盒子 | 声明式分组的 app 条目集合（按 scene/tag/用法），堆叠/整理/折叠照收；「图标文件夹」而非「文件文件夹」 | 仅 shell 域（desktop.at + 投影协议动词增量） |
| 资料盒子 | **背书用户指定的实际目录（非桌面）**，盒内展示真实文件（网格/缩略图）；DeskBox folder-backed 的受限采纳——目录不落在桌面、不搬家，盒子是目录的活视图 | v1 仅需目录绑定 + fs 读 + 缩略图管线（均已有，见下）；跨 app 文件操作语义（拖出为引用/复制）留与 [应用通信 RFC](auto-app-communication-v0.6.md) 衔接，排序上属下游 |

比原路线 B 轻一档：资料盒子 v1 不必等实体引用体系，目录路径绑定即可
（通信 RFC 依赖从「前置」降为「后续增强」）。

### 5.1 资料盒子与 file-manager 的 UI 共享接缝（候选，plan 阶段定）

| 接缝 | 形态 | 依据/成本 |
|---|---|---|
| a) 命名视图 face | 027 新增 `view box`（参数化起始目录）；桌面盒子位 = 宿主拆借渲染 027 会话的活面，事件直达 027 会话——复用 dashboard 已有的 `has_named_view` 发现与 face pin 底座（020 迷你播控先例） | 机制现成；且与「小组件出面板、钉桌面」统一为同一底座（桌面级 face 宿主），一次投入两处收益 |
| b) 共享组件包 | file_icon/filetree 等抽取到 `apps/common/fs`（沿 `apps/common/settings` 先例，namespace auto），shell 特权 pack 与 027 共用组件源 | 无跨会话渲染成本；但要立组件包纪律与双端验证门 |

已有资产证据：027 已有网格缩略图（`auto.image.thumb` → Plan 547 媒体
管线，PLAN-023 交付）与地址栏坍缩；`src/front/app.at` 目前仅单
`widget App`/`view`，**尚无命名视图**（接缝 a 需 027 侧新增）；
`apps/common/settings` 已立共享组件包先例（接缝 b 有形可依）。

小组件形态同裁定顺带收敛：DeskBox 部件是自由浮窗，我们是
DashboardPanel 统一面板——面板适合召唤式概览，资料盒子/mini face
钉桌面是「常驻」形态，两者互补；接缝 a 若落，即同一底座的两种挂载点
（面板格 vs 桌面层 z 槽），胶囊模式作折叠态词汇。

## 6. UI 参考清单（DeskBox 视觉层）

现状证据：desktop.at 图标卡为 `bg-white/10` + `rounded-lg` 级基础样式
类（desktop.at:192 附近），无材质与层次词汇——用户判断「桌面 UI 还
比较粗糙」成立。DeskBox 可参考的 UI 词汇表：

| 词汇 | DeskBox 做法 | AutoOS 对应落点 |
|---|---|---|
| 材质 | Mica/Acrylic 半透明模糊、不透明度可调、圆角/边框/文本描边 | 盒子卡片 backdrop-blur + 半透明（DSL 样式类近似可达；真亚克力取决于 iced 后端能力，plan 阶段探针） |
| 盒子卡片骨架 | WidgetShell：标题栏（glyph + 可编辑标题 + hover 显现按钮）+ 分隔线 + 内容槽 | DesktopSurface 盒子组件的骨架蓝本 |
| 密度与尺寸 | 紧凑密度档、每部件图标尺寸覆盖、文字尺寸 | 网格常量（8 列 × 80px/72px/48px）参数化即可 |
| 图标自定义 | 每部件可换 emoji/本地图片、独立背景图 | `__desktop_icons` 已有 color 徽标（badge_color_for），补 icon 覆盖位 |
| 折叠态 | smart capsule（hover 展开、敏感内容隐藏） | 盒子/部件折叠词汇（§3.1-4） |
| 动效 | 展开/收起动画、缓动、刷新率适配 | 沿 shell 既有过渡纪律，盒子展开/折叠补动效 |
| 全景背景 | 全局背景三模式（跟材质/统一图/全景分片） | 壁纸已有多键控（SD-04）；盒子透明度随壁纸联动可后置 |

## 7. 后续决策与范围控制

- 节奏裁定（2026-10-15 用户）：本文止于分析与裁定记录——盒子/
  资料盒子/UI 共享等功能细化**暂缓**，待用户明确提出整理桌面时，
  以本文 §4–§6 为需求侧输入启动 `/auto-plan:new`。
- 若立项：走 `/auto-plan:new`，域为 shell（desktop.at / 投影协议 v1.x
  增量动词），并回写 Design 25 S9 表面盘点（虚拟文件夹条目）对齐；
  本文档只提供需求侧输入。
- 资料盒子接缝选型（a/b）在 plan 内先探针后定；倾向 a（与小组件钉
  桌面共用底座），b 作为组件抽稳后的收敛方向，两者不互斥。
- 与 v0.6 三项 RFC（应用通信 / DevTools / 分期路线）正交，不抢占
  容量；通信 RFC 依赖降为后续增强（§5）。
- 待细化（plan 阶段）：盒子交互细节（堆叠展开形态、整理预览流、
  密度默认值）、UI 材质在 iced 后端的可达性、入口盒子与 dock/launcher
  的分组语义是否互通（同源声明复用）。
