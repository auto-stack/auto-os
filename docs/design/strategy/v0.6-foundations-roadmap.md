# v0.6 系统通信与 DevTools 的分期及应用依赖

日期：2026-10-04；用户确认两项为v0.6重点。此前版本主打范围继续保留；新增的是应用/AI集成公共基础，需进入容量评估，不能暗中压缩原主线。

| 顺序 | 结果 | 可以离线先做 | 不应现在做 |
|---|---|---|---|
| F0 | 两份RFC、能力/schema/golden样例 | 样例、协议测试、调用/故障状态、token基线设计 | 覆盖旧task/msg或冻结Batom二进制细节 |
| F1 | 两进程本地broker原型 | 新实验模块中的注册/发现/call/receipt | 修改未同步的四大app和主桌面 |
| F2 | task/stream/events、typed binding、MCP适配 | 契约测试与独立client/server，Notes/Launcher新增adapter | 立即迁移全部MCP/CLI接口 |
| F3 | DevTools共同schema和runtime adapter | 现有VTree数据离线转换、静态/动态fixture与diff | 重写旧F12、两backend渲染架构 |
| F4 | Inspector、两AutoUI backend、一个第三方样板 | 独立viewer与协议SDK原型 | 宣称任何第三方app均可完整debug |
| F5 | 跨app真实任务与发布证据 | Launcher→Notes capture、Agent查询/动作/diff | 以“28app都打开”替代协议联测 |

F1/F2与F3的schema工作可分别开展；真正runtime接入要等v0.5基线恢复。每步采用独立Plan/worktree，语言核心/平台改动留在对应仓；当前文件只是阶段设计，不分配不可见主力机的正式全局计划号，也不把一个大RFC当全实现计划。

## 应用接入契约

Notes：捕获服务返回幂等durable receipt，资产/来源用引用；Launcher：provider调用能力与UI动作区分；Reader：稳定locator和摘录服务；Blog：草稿rev与导出快照服务。它们已有首批app计划，内部capture envelope是领域DTO，不能再各自发明注册、授权、trace、错误、stream一整套系统协议。

AutoDown编辑器、copy-paste bin、Jade知识底座、AutoLens、AutoScape通过同一Service/Capability与DevTools能力协商接入。共享存储尚未实现时可以显式导出/import；不能以临时JSON拷贝宣称已经有跨应用共享知识对象。长期把实体引用接auto-man身份/版本体系，但不能把所有可变用户数据当不可变安装包。

## 三个月窗口的范围控制

建议将两项合成一条系统基础设施主线，先交付“本地通信最小面+统一观察/操作共同子集+两个应用/两个backend/一个第三方样板”。这是重要且可验收的v0.6新增交付，完整分布式能力、全面debugger和全部应用迁移明确留后续。

不能把这条主线当无成本追加：它需要与AC/AAC、Linux、Python、ROS2、auto-man和应用产品化一起排依赖、留验证窗口。建议降低同时全面产品化的应用数量，保留四大app与Launcher/Notes/Reader/Blog的明确小闭环；28app独立化不等于28个大产品全功能开发。

第一轮协议/平台探针结束后重估范围，再决定哪个增强功能移动到v0.7。不得擅自推迟已确认的Linux/编译器/包安装目标，也不在本草案虚构并发agent或具体开发速度。

## 研究与实现边界

通信RFC：[Auto应用通信](auto-app-communication-v0.6.md)。诊断RFC：[系统DevTools](system-devtools-v0.6.md)。这些文件中的接口、名称、transport与时间估算仍属建议；后续计划以真实源码与平台证据确定。与Chrome相比，跨应用和系统任务关联是有价值的扩展，是否体验更好须由实际任务完成率、诊断时间和Agent成本验证。
