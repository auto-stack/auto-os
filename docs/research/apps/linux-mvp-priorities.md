# 应用基本可用与 Linux 移植：首批优先级

日期：2026-10-29。性质：产品分期建议，供选择首批实施范围；不是已批准的工期、应用验收或 Linux 支持声明。不替代既有在途计划。

2026-10-29 用户进一步明确：**先达到每个应用的基础必要能力；通过后 Linux 支持与增强可并行，增强另开会话讨论。** 当前分工以[基础能力两类盘点](basic-capability-audit-20261029.md)为准：A 类 18 个可优先考虑 Linux（28 个登记入口去重为 27 个产品）；B 类 9 个先补齐/验收基本应用。下文保留此前的场景与发行分期研究，不作为当前执行顺序。

## 1. 此前场景分期建议（基础门通过后再选）

**首批主攻四个应用：Explorer → AutoTerm → Launcher → Notes。** 设置、系统日志和只读资源监视作为同批配套；计算器与时钟的基础功能可择机收尾，不为它们单开同等规模的产品主线。

第二批：Reader、Photos、Music、Todo。第三批：Video、Calendar、Weather、Kanban、Blog、Paint 的新增产品化范围。专业数据工具、聊天的新协议能力与游戏增强随后推进；既有旗舰和已批准应用计划继续原主线。

首批形成两条可真实使用的路径：

1. 启动应用 → 浏览自己的文件 → 用终端处理文件 → 查看错误和资源占用。
2. 找到资料 → 捕获到便笺 → 保存 → 退出重开 → 找回并导出。

Linux 验证从首批开始。代表样本选择 **Explorer + AutoTerm + Notes + Music**：分别覆盖文件系统、进程/PTY、中文编辑与持久化、音频/媒体。Music 的早期平台探针不等于首批承诺完成整个音乐库产品。

## 2. 排序依据和已知基线

按五个维度定性取舍：日常使用价值、发行是否必需、对其他应用的复用价值、距离可靠闭环的差距、Linux 风险。不采用尚无测量支撑的分数和精确工期。

本轮只读核对 `apps.manifest` 的 28 个注册入口，其配置路径均可找到 pac.at；这仅证明入口存在，不证明 gitlink 健康、实际启动或功能验收。未启动应用、未运行 Linux、未推进任何 app pin。

| 应用/方向 | 本轮读到的事实 | 对排序的影响 |
|---|---|---|
| Explorer | README 描述 001–006 已实施、待统一复审；已有多选、冲突处理、搜索、预览和分片传输 | 优先复核已有交付和补 Linux 文件语义，避免重写 |
| AutoTerm | README 支持声明仍是 Windows；Unix 路径明确尚未验证 | Linux 首批验证对象，不能从 portable-pty 依赖推导移植完成 |
| Launcher | 001 为 executing，已有查询/provider/action 内核与后续修复记录；002 标题仍是 Windows 宿主 | 先收敛已有 001；Linux 宿主另做有边界适配，不直接照搬 002 |
| Notes | 001 frontmatter 为 execution_done；docs/README 记载 r7、next=独立 final review，002/003 为 drafting；根 README 保留较早 needs_fix 叙述 | 先核实冻结版本和复审交接，完成可靠收存；状态不一致不自行判为已交付 |
| Reader | 001 为 executing；当前规范的导入边界为 TXT/Markdown，EPUB 在 003；README 有运行模式、导入大小等限制 | 先修完现有书库/恢复合同，再做单一文档格式的可行性；不能把 EPUB/PDF 当现成能力 |
| Music/Photos/Video | 有独立应用基线和前期研究，本轮未复现播放/解码功能 | 尽早探平台风险，完整产品按后续批次验收 |
| 系统设置 | 当前主要是 AutoOS 配置中心，有统一配置读写设计 | 首批完成自身设置；Linux 网络/音频/电源先接现有系统能力，另验接入 |

这些是文档/计划观察，不是新增实测。实施前复核 app HEAD、父仓 pin、WIP、现行 Spec 与测试入口；历史 app 文档中的 Demo 路径和 v0.6-dev 工作分支，以当前 AGENTS 的 `apps/auto-*`、main/detached 纪律为准，不在本次排序中修改子仓。

## 3. 首批应用的具体边界

| 顺序 | 应用 | 为什么先做 | “基本可用”必须完成 | 首批不扩大的范围 |
|---|---|---|---|---|
| 1 | `auto-explorer` | 文件是阅读、媒体、编辑和终端的共同入口；已有较厚基础 | 浏览真实目录；新建/重命名/复制/移动；批量冲突与取消结果准确；删除语义明确；打开方式可用，重启后收藏可恢复 | 云盘聚合、插件平台、复杂远程文件系统 |
| 2 | `auto-term` | Linux 下的开发、安装、诊断和应急入口；平台风险明显 | 真实 Linux PTY；运行系统 shell 与 ASH；中文输入/选择复制；resize/滚屏；Ctrl+C、退出与子进程回收；错误可见 | 先不替换仿真引擎或同时扩展远程、多机协作 |
| 3 | `auto-launcher` | 让真实应用和文件能被找到并打开 | 应用与有限文件搜索；键盘可操作；重复结果/失效路径可解释；慢查询不覆盖新结果；动作失败有反馈 | 插件市场、全盘语义搜索、任意 Agent 动作 |
| 4 | `auto-notes` | 日常高频、易验证保存可靠性，也能连接后续阅读与知识产品 | 快速录入文本；保存有明确结果；退出/重启回读；查询和导出；既有修复中的失败/恢复准入全部满足 | 全媒体收存、协作同步、知识图谱和完整跨 app 通信平台 |

Notes 与 Launcher 的现有验收项不因本表收窄而删除。这里只限制新增范围；原合同内未闭合的失败仍需完成，不以“首版简单一点”直接过审。

同批配套：

- **auto-os-config**：应用配置真实生效、保存/恢复和错误明确。网络、音量、电源、输入法接已有 Linux 系统组件；不能把配置编辑器当作已完成系统控制面板。
- **auto-syslog**：应用/后端故障能筛选并导出诊断；继续是 OS 内部组件。
- **auto-monitor**：先交付真实 CPU/内存/进程读取和刷新。终止进程等写操作待对象身份与权限验收后开放。
- **auto-calc / auto-clock**：适合作为小工具和输入/字体回归样板。时钟/秒表与后台闹钟分别声明，后者须验证关窗、休眠和会话恢复；不以 UI Tick 代替后台提醒。

建议同时保持最多两条应用实现主线，加一条 Linux/公共能力验证线；这只是容量建议，不是自动创建任务或并发代理的授权。首轮审计后再估工期。

## 4. 全部 28 个现有入口如何安排

“后批”表示新增投入和发布成熟度的顺序，不要求等待才能修复既有问题，也不撤销已批准主线。已具备可靠功能的应用经基线验收后可以先随发行提供。

| 批次/角色 | 应用 | 首个日用结果 |
|---|---|---|
| A 主攻 | Explorer、AutoTerm、Launcher、Notes | 完成上表四个可靠闭环 |
| A 配套 | OS Config、Syslog、Monitor | 可设置、可观察、可定位故障 |
| A 小工具 | Calc、Clock | 正确计算/复制；时钟与计时，提醒按实际支持单列 |
| B 内容与个人事务 | Reader | 先关闭 001 的真实书库/恢复问题；再选单一文档格式，做连续阅读/位置恢复/标注导出；EPUB 按既有 003 探针推进，PDF 单列能力决策 |
| B 内容与个人事务 | Photos | 文件夹看图、缩略图、缩放/方向、错误和不改原图的导出 |
| B 内容与个人事务 | Music | 本地文件/目录、队列、播放暂停/seek、设备错误和重启恢复 |
| B 内容与个人事务 | Todo | 本地任务创建/编辑/完成、重启恢复、筛选与导出；重复/提醒等待共同后台能力 |
| C 新增范围 | Video | 本地片源、字幕/音轨、seek、全屏和续播；复用已验证媒体链 |
| C 新增范围 | Calendar | 本地事件、时间/时区、ICS 导入导出；可靠提醒与重复例外另验 |
| C 新增范围 | Weather | 真实天气来源、更新时间、缓存和断网状态 |
| C 新增范围 | Kanban | 维持已有看板闭环，补持久化/导出/恢复；与 Todo 的共享先明确职责 |
| C 新增范围 | Blog | 已批准草稿工作继续；收敛本地草稿→预览→带资源导出，不扩社区/多用户发布 |
| C 新增范围 | Paint | 图片/截图裁剪、文字箭头标注、撤销和导出副本 |
| D 专业扩展 | Database、Charts | SQLite 浏览/查询/导出；CSV→图表→保存/导出，分别验收 |
| D 待定身份 | Chat | 先决定 AI 对话还是人际通信，再选对应数据/协议；既有已可用能力保留 |
| 已有休闲应用 | Tetris、Solitaire、Minesweeper | 验收当前规则、输入和存档后保留；新玩法不占首批主线 |
| 既有专项主线 | AutoMusk、AutoJade（旧称 Jade Garden；两个历史登记入口） | 继续既有计划；Linux 首版只承诺明确验收过的启动、项目/文档读写及必要系统接缝，不在本表重排内部研发 |

以上分组覆盖 28 个 manifest 入口；Jade Garden 与 AutoJade 是同一产品，去重为 27 个应用。**AutoShell/ASH 另列为既有主打能力**，与 AutoTerm 联测，但不是额外的 manifest 注册项，也不是桌面 Shell。基本文本编辑能力优先沿用现有编辑器；若首验环境尚不能运行，则明确采用外部编辑器补位，不临时再造一个新应用。

Reader 排版或运行模式若有硬阻塞，Photos/Music 可以先交付，Reader 探针继续；不要求整批应用互相等待。既有 Blog、Kanban 和旗舰计划也不因列在后批而暂停。

## 5. Linux 移植与应用实现同步推进

先冻结一个首验组合：基础发行版、CPU 架构、GPU/驱动、桌面会话、工具链/字体及固定 app pin；当前不擅自指定发行版或版本。

这里的应用移植验收是“能在约定 Linux 环境安装和使用”。既有平台规划中的 AutoOS 发行预览仍有独立的集成/安装/窗口与会话验收，遵循其工程重构和 RQHost 前置；环境调查与小探针可先开展。若目标包含自有会话或安装镜像，不能用现有桌面里的一个窗口替代发行验收，也不默认要求每个应用实现自己的合成器。

| 代表应用 | 早期 Linux 探针 | 不通过时的处理 |
|---|---|---|
| Explorer | 路径大小写/权限、符号链接本身与目标的操作语义、回收站/删除、复制中断；从系统文件入口打开 | 平台/FS 接缝独立登记，应用不隐藏数据错误 |
| AutoTerm | 真实 PTY、shell 路径、中文/emoji、全屏 TUI、Ctrl+C、resize、孤儿回收 | 明确 adapter 缺口，不能只做“Linux 编译成功” |
| Notes | 中文 IME/选区/剪贴板、用户目录写入、保存失败、关窗重开 | 优先修可靠性；不通过就不标日用完成 |
| Music | 音频输出、播放控制、设备切换/丢失、退出资源回收 | 冻结媒体引擎和接缝路线，避免 Music/Video 各实现一套 |

各 app 复用平台层：

- 应用启动入口与所支持 MIME 类型沿 [Desktop Entry](https://specifications.freedesktop.org/desktop-entry/latest/)；默认打开方式沿 [MIME Applications](https://specifications.freedesktop.org/mime-apps/latest/)。这些是接口依据，不是 AutoOS 当前兼容性声明。
- 配置、用户数据、状态、缓存与运行期文件区分，参照 [XDG Base Directory](https://specifications.freedesktop.org/basedir/latest/)。已有数据目录若需迁移，须另有可恢复的迁移合同，不能直接换目录导致旧数据不可见。
- 文件选择、打开 URI、通知、截图等按首验会话选择合适的 [XDG Desktop Portal](https://flatpak.github.io/xdg-desktop-portal/docs/) 接口和后端；消费既有 portal 与实现新的 AutoOS portal backend 是不同工作量，按发行形态选择，不默认全量自研。
- 中文字体/输入法、窗口焦点、DPI、剪贴板、通知和音频均需真实会话验证。各 Linux 结果只覆盖实测组合，不直接推广到所有发行版或显示服务器。

以上官方规范于 2026-10-29 打开核对。应用优先级是基于本仓目标和现有基线的产品判断，并非规范给出的排序。

浏览器、基础文本编辑、网络/音频/电源入口是发行日用配套。优先集成现有浏览器、编辑器和系统组件；办公、邮件等沿[前期组合建议](portfolio.md)采用外部产品。每项需验启动、输入、打开文件/URL和退出，不能仅列“随系统提供”。

## 6. 每个应用何时算基本可用

先为每个 app 写一页功能范围和真实任务，再接受以下结果：

1. 在干净环境安装后，用户无需开发机路径或手动修库即可启动和完成该任务。
2. 宣称可持久化的数据保存、退出、重启后可回读；有导出与恢复路径。
3. 空数据、损坏输入、权限/磁盘/网络错误和取消，返回可理解且真实的结果。
4. 核心流程的键盘、中文输入/字体、焦点、剪贴板、缩放可用；后台提醒/媒体单列验证。
5. 固定源码/依赖组合，在约定 Windows/Vue/VM 与 Linux 支持矩阵下分别留证；不以一端通过替代另一端。
6. 记录已支持、不支持及未验范围；支持范围内未通过项必须继续完成，不能只写进债务就标为已验收。

“基本可用”允许范围小，但已承诺范围内要可靠。Linux 首预览可只声明有限的已验应用集合；其余应用继续逐批产品化，不能由预览数量倒推取消全部应用最终可用的目标。

## 7. 此前候选实施入口（当前先完成基础盘点与 B 类补齐）

1. **OS 侧确认首验矩阵**：发行形态/环境、28 项基线状态和共享平台缺口；运行当前子模块健康闸门，保留源码 pin 与他人 WIP。此工作先于启动/集成验收，不把本轮 pac.at 盘点当作健康闸门。
2. **Explorer**：核实 001–006 的既有交付与验收边界，补本轮日用/平台差距；已归档计划不重开，新增缺口按新修复计划处理。
3. **AutoTerm**：立有边界的 Linux PTY/输入/生命周期验证，复用既有引擎，不先换内核。
4. **Notes / Launcher**：沿现有 001 处理复审/修复与收尾，再推进各自后续计划；先核实状态矛盾和真实冻结提交，不重建一套重复计划。
5. **Reader / 媒体探针**：Reader 先关闭 001 的存储/恢复问题；Music 跑早期平台探针，随后决定 Reader/Photos/Music 的交付次序。

OS 主改面的正式计划与债务在 AutoOS 登记；app 业务计划在对应 `apps/auto-*`；跨仓计划正文在主改面，其他仓保留指针和验收分工。当前只形成选择依据，不分配一批尚未就绪的实施计划，不改 manifest/Spec/端口/代码，不更新 submodule。
