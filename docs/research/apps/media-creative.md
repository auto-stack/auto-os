# 媒体与创作应用

日期：2026-10-22。功能材料为官方 README/产品页 A，mpv 许可读到文本 B；设计与引擎路线为 D。没有播放、解码或性能实测。

<a id="music"></a>
## 1. Music：以本地音乐库和稳定播放为中心

**市场**：流媒体订阅、桌面本地收藏与自托管音乐服务是不同层次。[Spotify](https://open.spotify.com/) 是内容服务参考，本次首页正文不可读取，不据此展开功能优劣；自有文件的管理/播放无需复制其内容分发模式。

| 候选 | 已核查优点 | 代价与取舍 |
|---|---|---|
| [Strawberry](https://github.com/strawberrymusicplayer/strawberry) | GPL-3.0 元数据；C++/Qt；README 列出本地收藏、格式、播放列表、MPRIS2/通知等 | 适合收藏者工作流；不把全部音频专家设置放首屏，也不整体移植 Qt UI |
| [Navidrome](https://github.com/navidrome/navidrome) | GPL-3.0；Go 服务；README 明确大库、多用户、元数据/监视和多端播放 | 是服务器，不是桌面解码库；连接它可扩展私有库，但首版不要求用户部署服务 |
| [mpv](https://github.com/mpv-player/mpv) | 多格式播放；有控制接口与 libmpv 路线候选 | 需验证音频输出、设备切换、队列和生命周期；具体构建许可不同 |

**综合设计**：最近/专辑/艺人/文件夹/搜索 + 正在播放队列。播放列表是用户资产；队列是当前执行状态，二者分开。拖入、追加、下一首、随机/循环、进度、音量、设备变化、媒体键与重启恢复要可靠。元数据按专辑艺人/合辑/多碟处理；扫描增量进行，坏文件不会卡住整库。封面、歌词、在线元数据和远端库为后续可关增强。

**实现路线**：保留用户提到的已有可用播放基础，先审查当前引擎/格式/状态，再比较复用现有媒体服务、mpv 进程控制或 libmpv。Auto 负责库、队列与交互，解码放成熟引擎/平台层；不在 app 写手工 Rust 后端。Web HTML 媒体、VM 原生音频的支持矩阵分开记录；不能把 Web 能播放一个文件算全部格式双端一致。

**门**：真实导入→扫描中播放→队列编辑→切换设备→暂停/恢复→退出重开。覆盖中文路径、损坏音轨、无权限文件、断设备、网络库失联；测切歌间隙、CPU/内存/后台耗电和扫描响应。无缝播放/ReplayGain 等只有实测后列入承诺。

<a id="video"></a>
## 2. Video：先可靠播放，再扩展媒体库

**市场**：本地万能播放器与流媒体平台分开。[VLC](https://github.com/videolan/vlc) 是跨平台多格式产品参考，GPL 元数据；[mpv](https://github.com/mpv-player/mpv) 是更适合研究可控播放内核的候选。VLC 的功能广度不等于 AutoOS 首版必须支持全部流协议。

**综合设计**：打开文件/目录、播放队列、字幕/音轨、速度、seek/逐段跳转、全屏、断点续播；显示真正的缓冲/解码错误和硬解状态。字幕编码/中英混排与缩放必须可读；不把“有画面”当音画同步、休眠恢复和长时稳定都通过。先本地媒体，网络/串流/投屏独立扩展。

**实现比较**：外部 mpv 进程 + [JSON IPC](https://mpv.io/manual/stable/#json-ipc) 容易先证控制链，但嵌入视频表面/全屏/输入/窗口生命周期仍需验证；libmpv 可能更适合整合渲染，但 GPU 上下文/纹理/合成接缝更复杂；VLC/libVLC 是备选，具体库许可另核对。不能以 child window 在一个系统上成功推导 Wayland/Windows/Vue 都可用。

许可依据：[mpv Copyright](https://github.com/mpv-player/mpv/blob/master/Copyright) 区分默认 GPLv2+ 与排除 GPL-only 文件后的 LGPLv2.1+ 路线，并明确构建开关本身不能替代许可核查；不要把它简单写成“mpv = LGPL”。编解码器/平台分发选项同样要固定到实际产物。

**门**：自建/许可语料含 H.264/H.265 等候选编码、多音轨/软字幕、可变帧率、损坏文件和高分辨率。按实际支持矩阵选择；测长时播放、seek、音画同步、窗口缩放/全屏、休眠、设备丢失。无法获得的硬解能力标 unsupported，不伪造硬解标志。

<a id="photos"></a>
## 3. Photos：目录查看优先，个人影像库后续

**市场**：轻量看图、个人照片管理/云备份、专业 RAW 工作流分层。[Google Photos](https://www.google.com/photos/about/) 是组织/检索/编辑与备份的商业体验参照；AutoOS 首版更接近本地看图与整理，云照片服务是后续产品。

| 开源参考 | 可吸收优点 | 取舍 |
|---|---|---|
| [nomacs](https://github.com/nomacs/nomacs) | GPL-3.0；跨平台图像查看器，README 包括 RAW/PSD 等格式定位 | 轻量真实文件查看；格式支持依赖解码器，不承诺所有图层/相机 RAW |
| [Immich](https://github.com/immich-app/immich) | AGPL-3.0；README 列出照片/视频、相册、备份、去重、多用户等 | 个人影像库/手机入口好参照；完整服务、数据库、索引/机器学习不是轻量查看器前置 |

**综合设计**：文件夹/时间线/相册，缩略图、大图缩放/旋转/EXIF、上一张/下一张、收藏/筛选；裁剪/调色先保存副本或非破坏编辑记录。删除要明确是相册移除、库记录删除、回收站还是原文件删除。相册是引用集合，不强制把用户目录搬进私有黑箱。

**实现路线**：复用 Explorer 的资源标识、watch、预览/缩略图候选服务；原图为真值，缩略图按内容版本/尺寸/方向缓存。重解码在后台 worker，方向/ICC/巨大像素图需要资源限制。人脸识别、语义检索、手机备份与多端同步独立扩展；本轮未审其模型及数据迁移方案。

**门**：大目录滚动、EXIF 旋转、透明图/色彩配置、损坏/巨幅图、原文件变更、删除与恢复；保证导出不改原文件、缓存不把旧图当新图。记录 Web/VM 支持的格式差异。

## 4. Paint：先做图像标注工具，再决定专业绘画

**市场**：截图标注、白板图解、专业绘画分别需要不同交互和文档模型。开源 [Excalidraw](https://github.com/excalidraw/excalidraw)（MIT）README 提供场景对象、图形/箭头、撤销、开放 JSON 与 PNG/SVG 导出；适合解释图/白板。开源 [Krita](https://krita.org/en/) / [源码](https://github.com/KDE/krita)（GPL 元数据）是专业绘画产品，不能用其笔刷/色彩系统的复杂度要求轻量 Paint。

**综合设计**：首版从图片/截图打开，裁剪、尺寸、画笔、矩形/箭头/文字、颜色/线宽、撤销重做，保存可编辑工程 + 导出副本。若用户确实需要无限画布，另设白板模式；若要压感/图层/复杂笔刷，先集成 Krita。首批不把三种画布塞成一个含糊工具。

**实现路线**：AutoUI 外壳 + 命令/场景模型；对象/编辑记录与渲染分开，保存后能继续编辑。Excalidraw 的 Web/React 组件可作 Web 嵌入候选，VM 需要自己的画布/文本/坐标接缝，不能称直接全端复用。栅格与矢量导出都标分辨率/字体处理，来源资源引用可迁移。

**门**：图片→文字/箭头→多次撤销/重做→重开工程→导出校验；DPI、中文字体、透明度、缩放后 hit-test、鼠标/键盘及超大画布预算。首版目标是可靠完成一张说明图，非笔刷数量。
