# 研究方法、条目模板与后续任务

日期：2026-10-22。初期目标是建立可追溯的候选集、设计组合和实现问题，不在没有试用/源码/用户证据时宣布“行业最佳”。

## 1. 资料库如何维护

目录按应用领域组织，每个专题同时包含市场定位、竞品/开源状态、可吸收设计、成本、综合方案、实现选项和验证。新发现先入来源目录并记录证据深度，再写关联专题，最后检查是否改变 portfolio。只改候选不等于变更已批准 Plan。

`sources.json` 保存本轮核查事实：项目/URL、日期、仓库描述/语言、聚合许可、是否归档、README 与源码/许可入口、少量固定 SHA。它不是包锁文件、SBOM 或许可证审核结论；`sources.md` 是可读索引。两者更新时同步日期/状态；不要无理由把主分支 HEAD 的旧判断沿用到新版本。

更新触发点：选入实施 Plan 前、候选主要版本/许可变更、一次可行性探针完成、用户实际任务反馈。没有设置定时器或自动抓取任务；是否周期维护另由用户决定。

## 2. 统一条目模板

新专题复制以下结构，保留稳定 `APP-<id>` / `COMP-<repo>` 标识便于引用。不要为填表编造数据。

```markdown
# 应用类别 / AutoOS app
日期 / 状态 / 研究者 / 关联 Plan 与 Spec

## 用户与市场
核心用户、频率、真实任务；消费/专业/个人/团队分层。
商业/开源/可见源码候选及官方来源；市场份额未知就明确未知。

## 现状基线
仓库路径、父仓 gitlink 与 app HEAD、是否有 WIP、功能/测试证据。
文档记载和本轮实际运行分别列出；缺检出不是缺功能。

## 竞品卡（每个产品一张）
身份/官网/源码/平台/固定版本/核查日期。
用户任务、关键流程、数据模型/格式、离线/同步/导出。
实现栈/模块/引擎与精确源码入口。
优点、代价、明确限制；与用户任务的关系。
开源状态、LICENSE/子组件/图标字体资源、维护/归档信号。
证据 A/B/C；未知事项及下一步。

## 对照任务
相同 fixture、操作路径、平台/硬件/版本。
成功/错误/恢复、耗时/资源、可访问性、数据可迁移性。
不可比较的部分与失败证据；截图只做界面证据。

## 综合设计（建议 D）
默认流程、信息架构、关键交互、数据职责、AI/系统接口。
取 A 的何种优点、舍 B 的何种成本；理由、替代与非目标。

## 实现与验证
自研/引擎/adaptor/外部集成的比较，平台/许可/依赖前提。
先行探针、可观察结果、验收场景、迁移/恢复与资源界限。
待定问题、责任领域、进入 Plan 的条件。
```

## 3. 如何做有意义的比较

以同一任务比较，避免把可选功能数量加总。先设底线：数据完整性、核心任务、平台可行性、可维护/许可，再评体验/性能/系统连贯性。底线失败不能用“界面漂亮”加分抵消。

| 维度 | 要找的证据 | 初期如何记录 |
|---|---|---|
| 用户价值 | 频率、痛点、替代成本、跨 app 收益 | 假设→用户观察；不伪造调研人数 |
| 正确性/恢复 | 真实文件、故障注入、重启/迁移/备份 | 未跑则 unknown，不填“通过” |
| 交互/可发现性 | 完成任务的步骤、焦点/键盘/中文/辅助功能 | 文档观察与实际试用分开 |
| 性能/资源 | 相同硬件/数据与 p50/p95/内存/后台消耗 | 不把库函数微基准当 app 体验 |
| 数据可控 | 离线、开放格式、导出/导入、来源/版本 | 导出格式存在≠往返无损 |
| 系统整合 | 关联/通知/媒体键/任务/诊断/领域调用 | 三种平台分别验证，不跨平台推断 |
| 维护成本 | 许可、依赖、API 稳定性、发布/迁移与测试 | 活跃 push 不是质量证明；star 不是市场份额 |

暂不填统一数值排名。需要打分时先按用户任务确定权重、证据置信与成本，然后让候选同条件跑任务；“unknown”应单列，不能算 0 或最高分。

## 5. 本轮明确未知

没有竞品安装试用、可复现性能比较、全部源码审计、安全审计、用户访谈、真实容量估算；没有确认所有应用的当前 pin 能力；没有冻结同步/协作/统一数据库、原生文档/视频嵌入或第三方窗口接入。对此已提供有输入、输出和停止条件的研究任务；进入实现应先消除对应阻塞，而非把“还需研究”写在最后然后照常依赖它。
